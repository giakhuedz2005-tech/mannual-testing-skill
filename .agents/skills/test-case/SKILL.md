# Manual Test Case Design and Audit

Produce a logically complete, maintainable manual test suite. Treat test-case count as an outcome of coverage analysis, not a target to preserve.

## Scope boundaries

- This skill covers browser/UI functional test design and persistence/integrity verification.
- Do not place API request steps, endpoint contracts, raw HTTP assertions, or Postman content in a functional sheet.
- `Test Data, Input` contains reusable `TD-*` IDs only. Concrete values belong in the downstream test-data dictionary generated by `$test-data-generator`.
- Every `TD-*` used in the test sheet must be defined in the companion test-data contract. The contract describes what data is required; it must not pre-generate the concrete value.
- Do not invent validation rules, semantic content checks, database tables, columns, messages, or cascade behavior that the approved sources do not establish.

## Choose an operating mode

Use **DESIGN** when creating cases for a new or narrowly scoped requirement.

Use **SUITE AUDIT** when the user asks to review, update, complete, optimize, split, merge, deduplicate, or synchronize an existing suite. Also use it for a large feature with multiple workflows, actors, lifecycle states, or cross-module effects.

Both modes use the same design rules. SUITE AUDIT additionally requires a before/after coverage and change report.

## Source-of-truth order

Resolve conflicts in this order:

1. The user's current instruction and explicitly approved decisions.
2. Approved requirements, acceptance criteria, business rules, and change requests.
3. Verified product behavior, UI specification, and confirmed database schema.
4. Test plan, risk register, and requirement-analysis artifacts.
5. Existing test sheets and historical examples.

An existing case is evidence of prior intent, not a requirement. If a rule is unclear, classify it as an ambiguity. Ask only when the answer would materially change scope or expected behavior; otherwise state a narrow assumption without presenting it as confirmed logic.

Distinguish:

- **Enforceable rule:** the system must accept, reject, transform, authorize, persist, or display something. This can define a pass/fail expectation.
- **Content guidance:** recommended language, translation order, style, or example quality without a validation requirement. Verify preservation/rendering only; do not expect rejection.
- **Unconfirmed behavior:** record as an ambiguity or assumption. Do not manufacture a test oracle.

## Core workflow

### 1. Build a requirement inventory

Extract atomic obligations from requirements, ACs, business rules, risks, defect fixes, and approved clarifications. For each obligation, record:

- source ID;
- actor and authorization boundary;
- trigger/input;
- expected UI outcome;
- persistence/integrity outcome;
- lifecycle or concurrency dependency;
- risk if it fails.

For an existing suite, map every current case to its primary obligation before changing the sheet. Flag unmapped cases, uncovered obligations, and obligations covered only by an unrelated matrix case.

### 2. Establish the three-tier hierarchy

Always design:

`Test Scenario → Test Condition → Test Case`

- **Scenario:** a business workflow or outcome, not a field or individual click.
- **Condition:** one testable rule, behavior, state, or authorization boundary.
- **Case:** one independently executable business outcome with a clear oracle.

Do not split scenarios only into positive and negative containers. Do not use vague conditions such as `Validate input`.

### 3. Design coverage by risk

Select only applicable dimensions:

- happy path and accepted partitions;
- required, format, and boundary validation;
- empty and zero-result states;
- ownership, role, session, and account status;
- stale state, concurrency, uniqueness, and double submit;
- cancellation, retry, timeout, partial failure, and recovery;
- lifecycle, deletion, cascade, atomicity, and orphan prevention;
- privacy allow-listing, safe rendering, export/file integrity;
- downstream and cross-module invariants.

Prioritize security, irreversible mutation, uniqueness, concurrency, atomicity, data loss, and privacy failures above cosmetic behavior. Apply EP, BVA, decision tables, state transition, pairwise, or error guessing only where the requirement model justifies them.

### 4. Set atomic case boundaries

Read [references/design-rules.md](references/design-rules.md) before creating or restructuring cases. Its split/group rules are mandatory.

Key invariant: group data partitions only when they exercise the same rule and produce the same observable UI message/state, persistence outcome, precondition, workflow, risk, and reset strategy. Otherwise split them.

A matrix case is acceptable only for one shared invariant, such as a role/action denial matrix. It must not duplicate feature cases that already prove the same outcome.

### 5. Design normalized test-data profiles

Read [references/test-data-contract.md](references/test-data-contract.md) before assigning or changing any `TD-*` ID. Its profile boundaries, contract schema, identifier rules, and bidirectional validation rules are mandatory.

Derive data profiles only after case boundaries and expected outcomes are stable:

1. Identify the actor, resource, input partition, lifecycle state, session, file, failure mode, matrix, or computed-data requirement used by each case.
2. Reuse a `TD-*` only when its full semantic meaning, state, ownership, generation rule, dependencies, isolation, and reset behavior remain compatible.
3. Split profiles when actor, resource identity, ownership, lifecycle state, target partition, expected behavior class, dependency, or reset strategy differs.
4. Assign stable IDs and place only those IDs in `Test Data, Input`.
5. Produce `Test data contract for <Feature>.tsv` alongside the test sheet. Use one row per field/attribute requirement and the canonical schema in the reference.
6. Link each contract row only to the `TC-*` cases that consume that row. Do not copy a profile-wide test-case list onto unrelated rows.

One profile may contain multiple fields only when they form one coherent fixture or transaction dataset. A partition set may share one profile only when the test case explicitly iterates the partitions and all partitions have the same rule, workflow, oracle, dependencies, and reset strategy.

### 6. Write executable cases

Each case must contain:

- a specific summary stating action, object, and condition;
- only the necessary preconditions;
- `Test Data, Input` with one or more IDs in the form `TD-...; TD-...` and no descriptions or literal values;
- numbered browser/user steps that reference the relevant `TD-*` profiles;
- a verifiable UI result and a persistence/integrity result;
- priority and concise technique/perspective metadata;
- traceability to its primary requirement/AC/risk when the sheet has no dedicated traceability column.

Steps must describe browser actions. Direct URL navigation, refresh, incognito, multiple browser sessions, and simulated environment failure are allowed. API calls are not.

### 7. Write evidence-based expected results

Use:

1. `[UI]` or `[UI/File]` for visible state, feedback, navigation, controls, and file contents.
2. `[DB]` for persistence, ownership, uniqueness, referential integrity, atomicity, defaults, and non-mutation.

The DB expectation must match the precision of confirmed schema knowledge:

- Use physical table/column names only when confirmed by project artifacts.
- Otherwise state the logical entity invariant and flag schema confirmation in `Execution Notes`.
- Do not claim a particular SELECT projection, RLS query result, or physical cascade implementation merely because it seems likely.
- For rejection/cancel/read-only operations, explicitly state the intended non-mutation.
- For stale deletion and concurrent mutation, verify atomic failure and absence of orphan or partial records.

Expected results must correlate with the actions and data partitions, but they do not need artificial one-result-per-click wording. State exact messages only when specified or observed; otherwise describe the required user-facing meaning.

### 8. Audit the suite before delivery

For DESIGN, verify coverage, uniqueness, hierarchy, traceability, test-data contract consistency, and format.

For SUITE AUDIT:

1. Compare the requirement inventory with the existing coverage map.
2. Remove cases that only duplicate another case without a distinct layer or risk.
3. Split cases that combine different rules, causes, outcomes, or persistence paths.
4. Add missing positive, negative, boundary, authorization, concurrency, recovery, and integrity cases only when supported by scope.
5. Synchronize preconditions, data IDs, steps, expected results, priority, and notes after every structural change.
6. Preserve execution results and evidence for unchanged cases.
7. Preserve stable IDs when case meaning remains unchanged. Do not renumber executed/historical cases unless the user explicitly requests it. A draft suite may be renumbered contiguously when required by project convention.
8. Synchronize the companion test-data contract after every added, removed, split, merged, or repurposed `TD-*` reference. Retire orphaned profiles and preserve stable profile IDs whose meaning is unchanged.

Deliver a change report containing:

- case count before and after;
- cases added, removed, split, merged, or materially rewritten;
- coverage gaps closed and duplicate coverage removed;
- unresolved ambiguities or schema dependencies;
- validation commands and results.

## TSV delivery

When producing or editing TSV, read [references/tsv-delivery.md](references/tsv-delivery.md) and follow it exactly. Preserve the supplied template header and column order verbatim; otherwise use the canonical schema in that reference.

When the suite uses `TD-*` references, also produce or update the companion contract according to [references/test-data-contract.md](references/test-data-contract.md). The test sheet and contract are one delivery unit; do not hand off one with stale references to the other.

Run the deterministic validator when available:

```powershell
powershell -NoProfile -File scripts/validate-test-sheet.ps1 -Path '<test-sheet.tsv>'
powershell -NoProfile -File scripts/validate-test-data-contract.ps1 -TestSheetPath '<test-sheet.tsv>' -ContractPath '<test-data-contract.tsv>'
```

Use `-ExpectedHeaderPath '<template.tsv>'` when the project supplies a custom template.
Use `-RequireContiguousIds` with the contract validator only for a new draft; omit it when stable historical IDs must be preserved.

## Final quality gate

- Every requirement/AC in scope has intentional coverage or an explicit gap.
- Every case has one primary business outcome and belongs to one condition and scenario.
- Different validation rules, state causes, authorization paths, or persistence effects are not hidden in one case.
- No case duplicates another case without a documented distinct purpose.
- Positive, negative, boundary, state, security, concurrency, recovery, and integrity coverage is proportional to risk.
- Test data cells contain IDs only and each ID keeps one stable meaning.
- Every test-sheet `TD-*` resolves to at least one contract row; no contract profile is orphaned.
- Contract links are exact at row level: every linked `TC-*` consumes that profile field/attribute, and every consuming case is listed.
- Distinct actors, resources, ownership contexts, lifecycle states, sessions, failure modes, or reset strategies do not share one profile merely for convenience.
- The contract contains generation requirements and constraint sources, not concrete values or invented product rules.
- Steps, data IDs, expected results, priority, and traceability agree.
- UI and DB expectations are verifiable and do not invent product or schema details.
- Existing execution results are preserved; new results are `NOT RUN`.
- TSV structure, encoding, and row flattening are valid.
