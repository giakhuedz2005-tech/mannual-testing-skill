# Workflow: Bug Report from Test Execution

## Purpose and boundaries

Create one or more Markdown bug reports in the format used by the supplied sample. The skill consumes the test specification produced by `$test-case` and real execution results, then turns a verified expected-versus-actual discrepancy into a clear, reproducible report.

This skill creates report artifacts only. It does not execute tests, generate test data, change a defect tracker, or claim a defect when the available evidence is insufficient.

## Required input

Obtain both sources before creating a bug report:

1. **Test-case source** — the TSV generated by `$test-case`, or an equivalent exported test specification. It must provide at least `Test Case ID`, summary, preconditions, steps, expected result, priority, test-data reference, and feature/module context.
2. **Actual execution results** — a result sheet, execution export, or explicit run notes mapped to `Test Case ID`. For every candidate defect it must state run status and the observed actual result. Include executed data, environment, time/date, evidence links or reproducibility information when available.

Do not create a report from a `NOT RUN`, `Pass`, skipped, or missing result. If a failed status has no observed behavior, no expected-result reference, or no identifiable test case, ask for the missing evidence instead of inventing it.

## Import and normalize the source test cases

The `$test-case` TSV is a flattened hierarchy. Import it as tab-separated data and reconstruct inherited metadata before matching execution results:

- Forward-fill `Screen`, `Test Scenario ID`, `Test Scenario Name`, and `Test scenarios' Precondition overall` from the latest non-empty row.
- Forward-fill `Test Condition ID` and `Test Condition Name` from the latest non-empty row within that scenario.
- Treat each non-empty `Test Case ID` row as a distinct executable case.
- Read content from the semantic columns `Test Preconditions`, `Steps`, and `Expected Result`.
- Use `Test Data, Input` as the data-profile reference. Actual values used during a run must come only from the execution result or its linked test-data artifact.

Join the execution record to the normalized case by exact `Test Case ID`. Preserve the original execution evidence; do not overwrite the test-case TSV or alter actual results.

## Decide whether a report is warranted

Create a report only when an execution result establishes all of the following:

- The target case was executed and failed, or an equivalent observed anomaly is documented.
- The observed behavior differs materially from the test case's expected result or a confirmed requirement.
- The report can state enough reproducible context without guessing missing facts.

Group test runs that demonstrate the same underlying behavior into one bug; do not create duplicates merely because multiple test cases expose it. Keep an internal mapping to all source `TC-*` IDs used to support each issue, even though the sample format does not add a separate test-case field.

When the expected behavior, product rule, or observed evidence is ambiguous, create a report only if the user requests suspected issues. Mark it with `Status Recommendation: Need Clarification / Suspected Bug`; describe the uncertainty precisely and do not present it as a confirmed defect.

## Build the report fields

Use confirmed information from the normalized test case and execution result:

| Report field | Source and rule |
| --- | --- |
| Bug ID | Use the project tracker convention. If none is supplied, use `<PROJECT>-<MODULE>-<NNN>` consistently; never reuse an ID. |
| Summary | Concise symptom + affected object/behavior. State the observed failure, not a proposed fix or root cause. |
| Module | Derive from `Screen`, scenario/condition context, or supplied module mapping. |
| Environment | Copy actual run environment: product/build, URL, browser/device, OS, and execution date when available. Do not assume the sample's environment. |
| Precondition | Start with relevant test preconditions and include only run state essential for reproduction. |
| Steps to Reproduce | Use the executed path from the test-case `Steps`, adjusted only to include real setup/test data required to reproduce. Keep numbered actions. |
| Test Data | State the concrete data used in the run when captured. Otherwise retain the `TD-*` profile and explicitly say concrete run values were not captured; do not invent values. |
| Actual Result | Copy the observed behavior from execution evidence in neutral, factual wording. |
| Expected Result | Derive from the matching test case's expected result or a confirmed requirement; do not strengthen an ambiguous expectation. |
| Severity | Rate impact: `Critical` (blocker, data loss, security), `High` (major feature/business flow unavailable), `Medium` (incorrect significant behavior with workaround), `Low` (minor impact). Use project policy when provided. |
| Priority | Use the test case priority as a starting signal, then apply supplied triage policy/business urgency. Do not equate priority with severity automatically. |
| Reproducibility | Use only observed evidence: `Always`, `Intermittent`, `Once`, or `Not reproduced`. |
| Status Recommendation | Optional; include only for a suspected issue, requirement ambiguity, or another explicit triage state. |

Never insert credentials, production personal data, or sensitive tokens. Redact them while retaining a safe description of the data profile.

## Output format

Write output in professional English unless the user asks for another language. Follow this exact heading order and Markdown style for every issue. Put a blank line between consecutive report blocks; do not add unrequested headings such as root cause, fix recommendation, or test-case ID.

```markdown
**Bug ID:** <BUG-ID>

**Summary:** <observed symptom>

**Module:** <module>

**Environment:**

* <product/build>
* URL: <url>
* Browser/Device: <browser or device>
* OS: <operating system>
* Date: <execution date>

**Precondition:**

* <precondition 1>
* <precondition 2>

**Steps to Reproduce:**

1. <action>
2. <action>

**Test Data:**

* <executed data or TD-* reference>

**Actual Result:**  
<observed behavior>

**Expected Result:**  
<expected behavior>

**Severity:** <Critical | High | Medium | Low>

**Priority:** <High | Medium | Low or project value>

**Reproducibility:** <Always | Intermittent | Once | Not reproduced>

**Status Recommendation:** <optional>
```

Omit the optional `Status Recommendation` section for normal confirmed defects. Avoid Markdown tables for the final report because the sample is a sequence of standalone readable issue blocks.

## Quality gate before delivery

- Every report links internally to at least one executed `TC-*` and execution result; no report is based solely on requirement interpretation.
- Actual Result is observed evidence, Expected Result is from the matched case/confirmed requirement, and the two explicitly conflict.
- All reproduction steps, environment details, and test data reflect the executed run; missing facts are called out rather than fabricated.
- Bug IDs are unique; duplicate failures are consolidated only when symptom, affected behavior, and likely defect are the same.
- Severity, priority, and reproducibility are evidence-based and use permitted project values.
- The Markdown heading order, bold labels, bullet lists, and optional status section conform to the sample format.
